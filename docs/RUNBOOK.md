# Keekar's Pi VPN — replication runbook

Single, ordered, start-to-finish procedure to stand up this project (web
config UI + dual-mode WireGuard) on a Raspberry Pi, incorporating every
non-obvious problem already discovered and fixed once on the real device
(`pi0w-1`, `192.168.1.19`). Follow this top to bottom on a fresh device
rather than re-deriving any of it. This is the **executor reference** —
brief "why" callouts are inline, but the full incident narratives, design
tradeoffs, and research rationale live in
[`docs/PROJECT_NOTES.md`](PROJECT_NOTES.md); don't duplicate that content
here, link to it.

**Automated path**: everything below (except SSO/Authentik provisioning,
which needs a real client secret only a human can supply) is encoded in
`deploy/deploy.sh`, run from this repo on your Mac — it drives the Pi
entirely over SSH and is safe to re-run against an already-deployed
device (idempotent: skips what already exists, never touches a
pre-existing TLS cert or `sso.env`, and — critically — never
enables/starts/restarts a WireGuard *client*-role tunnel like `Syd-Home`,
per the safety note in §9.4):
```bash
PI_HOST=user@host ./deploy/deploy.sh          # full bootstrap + update
./deploy/deploy.sh --skip-deps                 # faster iteration, skip apt/pip
./deploy/deploy.sh --only <function_name>      # run a single step
```
It also runs `provision_tls_cert` (upgrades the self-signed cert to a real
Let's Encrypt one via DNS-01 once `ACME_EMAIL` and a Cloudflare token are
in place — see §5b) and installs `deploy/maintenance.sh` via a cron.d
drop-in (`/etc/cron.d/pi-config-ui-maintenance`) covering
health-check-and-restart (every 10 min — including restarting any
`SERVER_TUNNELS`-listed WireGuard server tunnel found enabled-but-inactive;
client-role tunnels are never touched, see §9.4), a DDNS updater (also
every 10 min — see §5c), a TLS cert-expiry health check (real renewal
happens independently via acme.sh's own cron + reload hook — see §5b),
weekly disk/log cleanup, a weekly `apt-get update`/`upgrade` on
Wednesdays at 05:00 (conservative `upgrade`, not `dist-upgrade`; also
snapshots pre-upgrade package versions for §5d's rollback path), and an
unconditional weekly reboot Wednesdays at 05:30 — right after that same
update, not days later, so a regression is caught the same morning (see
§5d for the full failsafe this enables). It also installs
`pi-config-ui-boot-check.service` (§5d — a post-boot health check that
restarts/best-effort-rolls-back and alerts if something's broken; also
see §5e for the related "how long was this device down" dashboard
feature) and drops a `logrotate` config for the maintenance cron jobs' own
log file (`/var/log/pi-config-ui-maintenance.log`) — nothing else rotates
a plain file that six jobs append to forever — see the scripts themselves
for the exact behavior. The manual steps below are what the script
encodes; use them for a first-time understanding of the system or if you
need to do something the script doesn't cover.

## 0. Target hardware assumptions

Designed and verified against the weakest realistic target: original
**Raspberry Pi Zero W**, single-core 1GHz ARMv6 (`armv6l`,
ARM1176JZF-S/BCM2835), 512MB RAM shared with the GPU — not the quad-core
Zero 2 W. Confirm with `uname -a` / `free -h` before assuming otherwise; if
the real device is stronger, everything here still applies, just with more
headroom. OS is `Raspbian GNU/Linux 13 (trixie)` — nftables-native, no
`iptables` binary by default (§7 below), NetworkManager-managed networking
(not `dhcpcd`).

## 1. Base OS network sanity (do this before anything else)

Raspberry Pi OS + NetworkManager + `resolvconf` has produced DNS failures
**twice** on this project, in different ways, on the same device. Check
both before moving on — five minutes here saves hours of debugging
downstream steps that all assume working DNS:

```bash
cat /etc/resolv.conf                # must show real `nameserver` lines
ls -la /etc/resolv.conf             # must be a symlink -> /run/resolvconf/resolv.conf
getent hosts google.com             # sanity: does DNS work at all
getent hosts <your-sso-hostname>    # sanity: does it resolve the SPECIFIC name you need
```

**If `/etc/resolv.conf` is a plain file, not a symlink**: `resolvconf`'s
update hook silently refuses to write to it (a safety check — visible as
`/etc/resolvconf/update.d/libc: Warning: ... not a symbolic link` in
`journalctl -u NetworkManager`), leaving it stuck at just
`# Generated by NetworkManager` with zero `nameserver` lines even though
`nmcli` shows correct DHCP-provided DNS. Fix:
```bash
sudo mkdir -p /run/resolvconf
sudo rm -f /etc/resolv.conf
sudo ln -s /run/resolvconf/resolv.conf /etc/resolv.conf
sudo resolvconf -u
sudo systemctl restart NetworkManager
```

**If a specific internal hostname fails to resolve while public ones
work**: a stale static override may be taking priority over DHCP:
```bash
cat /etc/resolvconf/resolv.conf.d/head   # should normally be empty/absent
```
If it hardcodes a `nameserver` line, that resolver gets queried first,
ahead of whatever NetworkManager/DHCP actually detected — clear it if
unintentional:
```bash
sudo cp /etc/resolvconf/resolv.conf.d/head /etc/resolvconf/resolv.conf.d/head.bak
sudo truncate -s 0 /etc/resolvconf/resolv.conf.d/head
sudo resolvconf -u
```
Also prioritize the resolver that actually knows your internal zone, as a
second layer of defense:
```bash
sudo nmcli connection modify <connection-name> ipv4.dns "<internal-dns-ip> 1.1.1.1" ipv4.ignore-auto-dns yes
sudo nmcli connection up <connection-name>
```

A single flaky Wi-Fi reconnect can also *transiently* produce an empty
`resolv.conf` even when the underlying config is correct — don't chase a
fix from one snapshot; re-check once the link has been stable a minute.

## 1b. Physical-console Wi-Fi recovery (HDMI + keyboard fallback)

If this Pi ever loses Wi-Fi entirely (moved location, SSID/password
changed), the web GUI becomes unreachable too — it's only served over the
network the Pi itself needs to be on. `deploy/maintenance.sh`'s
`wifi-recovery-console` subcommand is a `whiptail`-based console tool for
exactly that case, launched automatically — no SSH/network needed to
reach it. Consolidated into `maintenance.sh` (alongside every other
on-Pi script — one file to lint/test/maintain instead of several) rather
than living in its own standalone script; the two systemd units below
still exist separately, since they represent different privilege/TTY
lifecycles, not just different code.

**Uses the same `nmcli` commands `app/network.py`'s GUI Wi-Fi feature
does** (`device wifi list`, `device wifi connect <ssid> password <psk>`,
`connection show`) against the same
`/etc/NetworkManager/system-connections/` profile store — a network added
via either one is immediately visible/usable in the other, no sync logic
needed. They also can never run at the same time in practice: the console
only ever launches when there's no working connection, which is exactly
when the GUI is unreachable. Multiple saved networks failing over to
whichever is actually in range is inherent NetworkManager `autoconnect`
behavior once more than one profile exists — not something this tool
implements, just something adding more profiles benefits from for free.

**Two triggers, one idempotent gate** (`maintenance.sh`'s
`wifi-recovery-check` subcommand, run by `wifi-recovery-check.service`):
checks
`/sys/class/drm/card*-HDMI-A-1/status` for `connected` (confirmed on the
real device to use the modern KMS graphics stack, not the legacy
`tvservice`) and `nmcli networking connectivity check` (must run as
root — an unprivileged user gets "Not authorized"); if either isn't met,
it's a no-op. This same idempotent check runs both at boot
(`WantedBy=multi-user.target`, `After=NetworkManager-wait-online.service`
— covers a monitor already attached when it can't connect) and on every
HDMI hotplug event (`deploy/udev-rules/99-wifi-recovery.rules`, matching
any DRM `change` event and letting the gate's own status check determine
whether it actually means HDMI — covers plugging a monitor in later while
already stuck headless). Since it's a real systemd service,
`systemctl start` on an already-running instance is a safe no-op — rapid
plug/unplug/plug can't stack multiple recovery consoles.

**Two systemd units, deliberately split** (`wifi-recovery-check.service`
+ `wifi-recovery-console.service`), not one: the console needs
`TTYPath=/dev/tty1` (the same mechanism `getty@.service` itself uses —
whiptail's ncurses UI needs a real controlling-terminal session for
keyboard input, not just file-descriptor redirection to `/dev/tty1`) to
take over the physical console, but `getty@tty1.service` must be fully,
synchronously stopped *first* or the two fight over the same tty. Putting
both concerns in one unit risks a race between that unit's own `TTYPath`
setup and getty still holding the tty; splitting them lets
`cmd_wifi_recovery_check` call `systemctl stop getty@tty1.service`
(blocks until fully stopped) and only then `systemctl start
wifi-recovery-console.service` (which runs `cmd_wifi_recovery_console`),
eliminating the race. `wifi-recovery-console.service` is never enabled —
only ever started this way. A `trap ... EXIT` in
`cmd_wifi_recovery_check` always restores `getty@tty1` afterward, even if
the console unit errors or is interrupted. This is also why these two
pieces stay two separate systemd units even though the *scripts* were
consolidated into one file — the unit split reflects a real TTY-ownership
boundary, not just code organization.

**A consolidation gotcha worth knowing if you touch this code**: both
subcommands were originally standalone scripts with `set -uo pipefail`
(no `-e`), since nmcli/whiptail returning non-zero — Cancel pressed, a
connect attempt failing — is normal control flow there, not a script
error. `maintenance.sh` itself uses the stricter `set -euo pipefail`.
Moving the code in without accounting for that difference would have been
a real regression: under `-e`, an unguarded failing command aborts the
*entire* `maintenance.sh` process immediately at that line, even one
followed by an explicit `return` on the very next line — e.g. pressing
Escape on a plain informational `--msgbox` would otherwise kill the whole
recovery console instead of just dismissing that dialog. Every
nmcli/whiptail call in `cmd_wifi_recovery_console` and its `wifi_*` helper
functions is explicitly guarded (`|| true`, `|| return 0`) as a result —
keep that guard when editing or adding to this code.

**Verified live on the real device** (stopping `getty@tty1` and manually
starting `wifi-recovery-console.service` over SSH, confirmed via `ps` and
`/proc/<pid>/cmdline` byte inspection — not by physically watching a
screen): the console correctly attaches to tty1, reads live `nmcli`
state, renders real newlines (not literal `\n` — an actual bug caught and
fixed this way), and `getty@tty1` is cleanly restored afterward. Re-run
after any change to this code — same commands, no monitor needed:
```bash
sudo /opt/pi-config-ui/maintenance.sh wifi-recovery-check   # HDMI disconnected -> should no-op, check the journal
sudo journalctl -t pi-config-ui-maintenance --no-pager -n 5
sudo systemctl stop getty@tty1.service
sudo systemctl start --no-block wifi-recovery-console.service
sleep 3 && ps aux | grep whiptail   # confirm it attached to tty1
sudo systemctl stop wifi-recovery-console.service
sudo systemctl start getty@tty1.service   # confirm this comes back cleanly
```
**Not verified, and can't be without physical access**: the actual visual
rendering on a real monitor, and a genuine HDMI hotplug event triggering
the udev path — test both once you have physical access.

**Install** (already wired into `deploy/deploy.sh`'s `install_wifi_recovery`,
run as part of a full `./deploy/deploy.sh` pass):
```bash
sudo cp deploy/wifi-recovery-check.service /etc/systemd/system/
sudo cp deploy/wifi-recovery-console.service /etc/systemd/system/
sudo cp deploy/udev-rules/99-wifi-recovery.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules
sudo systemctl daemon-reload
sudo systemctl enable wifi-recovery-check.service   # not wifi-recovery-console — never enabled
```

## 2. Install the app

```bash
sudo useradd --system --no-create-home --shell /usr/sbin/nologin pi-config-ui
sudo mkdir -p /opt/pi-config-ui
# copy the repo's app/, deploy/, requirements.txt (not local dev artifacts) here
sudo chown -R pi-config-ui:pi-config-ui /opt/pi-config-ui

sudo -u pi-config-ui python3 -m venv /opt/pi-config-ui/venv
sudo -u pi-config-ui /opt/pi-config-ui/venv/bin/pip install \
  --index-url https://www.piwheels.org/simple \
  -r /opt/pi-config-ui/requirements.txt
```
**Use piwheels, not plain PyPI**: `psutil`, `pyroute2`, and `cryptography`
(an authlib transitive dep) have C extensions with no upstream `armv6l`
wheels on PyPI — without piwheels, pip compiles from source, slow on a
1GHz single core. With piwheels this completes in a few minutes.

## 3. TLS certificate trust for the SSO/IdP connection

Check **before** configuring SSO, not after — a trust failure here looks
identical to a misconfigured client and wastes time in the wrong place:
```bash
curl -v https://<your-sso-hostname>/ 2>&1 | grep -i "certificate\|SSL"
```
If it fails to verify: the IdP's cert may chain through a very recently
introduced CA root (e.g. Let's Encrypt's 2026 "Generation Y" `ISRG Root
YR` hierarchy) not yet trusted by Python's `certifi` bundle *or* the OS's
own `ca-certificates` package — even though `app/auth.py` already uses the
`truststore` package (OS-native trust store, not a pinned bundle)
specifically to avoid the `certifi`-lag half of this problem. Diagnose
with `openssl s_client -connect <host>:443 -showcerts` to see the actual
issuer chain, fetch the specific missing root from the CA's official certs
page, verify its fingerprint/subject before trusting it, then:
```bash
sudo cp <root>.pem /usr/local/share/ca-certificates/<root>.crt
sudo update-ca-certificates
```
Re-run the `curl` check to confirm before moving on.

Separately: this CPU's TLS handshakes are slow (RSA/ECDHE math on ARMv6
with no crypto acceleration — observed ~5.7s for a single handshake).
`app/auth.py` sets an explicit `"timeout": 20` on the OAuth client for
exactly this reason — don't remove it, and give any other outbound HTTPS
call on this device a generous timeout too, or it will intermittently fail
with a connect-timeout that has nothing to do with the network.

## 4. SSO / Authentik configuration

1. Provision a dedicated OIDC application on the Authentik instance for
   this device, giving you a client ID/secret and the application's URL
   slug.
2. ```bash
   sudo mkdir -p /etc/pi-config-ui
   sudo cp deploy/sso.env.example /etc/pi-config-ui/sso.env
   sudo chmod 600 /etc/pi-config-ui/sso.env
   ```
   Fill in:
   ```env
   SSO_ISSUER=https://sso.keekar.au
   SSO_APPLICATION_SLUG=raspberry-pi
   SSO_CLIENT_ID=raspberry-pi
   SSO_CLIENT_SECRET=<real secret>
   SSO_REDIRECT_URI=https://<your-hostname>/auth/callback
   SESSION_SECRET=<openssl rand -hex 32>
   ```
   - **`SSO_APPLICATION_SLUG` is not the same as `SSO_CLIENT_ID`**, even
     when they share a value. Authentik serves OIDC discovery
     per-application at `/application/o/<slug>/.well-known/openid-configuration`,
     not at the issuer root — `app/auth.py` builds the discovery URL from
     the slug specifically. Using the issuer root 404s and login never
     gets past the first request.
   - **Never use a `.local` hostname for `SSO_REDIRECT_URI`.** `.local` is
     reserved for mDNS/Bonjour on essentially every modern client — this
     Pi's own `/etc/nsswitch.conf` intercepts `.local` names via
     `mdns4_minimal [NOTFOUND=return]`, meaning it **never falls through
     to real DNS at all**, regardless of what records exist there; macOS
     and Android behave the same way. Use a real hostname under a DNS zone
     you control, and register that exact URI on the Authentik client.
   - The redirect URI's port must match how the app is actually served
     (§8) and match the Authentik client exactly — a mismatch fails
     silently as a generic "Login failed," not an obvious error.
3. Confirm `app/auth.py`'s OAuth client registration still has
   `"code_challenge_method": "S256"` in `client_kwargs` — authlib's
   `authorize_redirect()` does **not** add PKCE automatically; this is a
   "don't accidentally remove it" callout, not a step to perform.

## 5. TLS keypair for the app itself

```bash
sudo mkdir -p /etc/pi-config-ui/tls
sudo openssl req -x509 -newkey rsa:2048 -sha256 -days 825 -nodes \
  -keyout /etc/pi-config-ui/tls/key.pem -out /etc/pi-config-ui/tls/cert.pem \
  -subj "/CN=<your-hostname>" \
  -addext "subjectAltName=DNS:<your-hostname>,DNS:<pi-hostname>,IP:<pi-lan-ip>"
sudo chown -R pi-config-ui:pi-config-ui /etc/pi-config-ui/tls
sudo chmod 600 /etc/pi-config-ui/tls/key.pem
```
Self-signed is fine for LAN-only use; replace with a real cert if this
needs to be reachable from outside the LAN.

## 5b. Upgrading to a real (Let's Encrypt) certificate

Only needed if the app's hostname needs to be trusted by a real browser
(no "not secure" warning) rather than just reachable on the LAN.
`deploy.sh`'s `provision_tls_cert` automates everything below except step
1 (secrets are never handled by the script — same convention as
`sso.env`), and is safe to re-run: it detects an already-CA-issued cert and
leaves it untouched.

**Why acme.sh (not certbot), and why DNS-01 (not HTTP-01):**
- `acme.sh` is a pure shell script with no Python/venv overhead — a
  meaningfully lighter footprint than certbot on this CPU (§0).
- If this Pi's public DNS record for its hostname resolves to a **private**
  LAN IP (check with `dig +short @1.1.1.1 <hostname>` — true for this
  project's `vpn.bpl.keekar.au`, which intentionally points at the Pi's LAN
  IP), Let's Encrypt's HTTP-01/TLS-ALPN-01 validation can never reach the
  device from the public internet, no matter what's port-forwarded.
  DNS-01 only needs API access to create a `_acme-challenge` TXT record —
  it doesn't care what the A record resolves to.

**Steps:**
1. In the Cloudflare dashboard (the DNS host for this project's zone): My
   Profile → API Tokens → Create Token → "Edit zone DNS" template,
   restricted to this specific zone only (least privilege — not the
   account-wide Global API Key). SSH into the Pi yourself and store it
   where `provision_tls_cert` expects it:
   ```bash
   sudo sh -c 'umask 077; printf "CF_Token=%s\n" "<paste-token>" > /root/.cf-dns-token'
   ```
2. Run the deploy script with an email for the Let's Encrypt account
   (used only for expiry-related notices):
   ```bash
   ACME_EMAIL=you@example.com ./deploy/deploy.sh --only provision_tls_cert
   ```
   Or, for a full deploy pass that also provisions the cert:
   ```bash
   ACME_EMAIL=you@example.com ./deploy/deploy.sh
   ```
3. This installs `acme.sh` under root, registers a Let's Encrypt account,
   issues the cert via `--dns dns_cf`, and installs it to
   `/etc/pi-config-ui/tls/{key,cert}.pem` with a `--reloadcmd` that fixes
   ownership/perms and restarts `pi-config-ui`. `acme.sh`'s own root cron
   (installed by its installer, independent of this project's
   `/etc/cron.d/pi-config-ui-maintenance`) handles renewal automatically
   going forward, firing that same reload hook only when a renewal
   actually happens.
4. `maintenance.sh`'s `cert-renew` cron entry (daily) is a health check
   only, not the renewal mechanism — it logs a warning if the live cert is
   within 14 days of expiry without having renewed, which would indicate
   acme.sh itself has silently broken (check `acme.sh --list` and
   `journalctl` on the Pi if that fires).

**Verify:**
```bash
curl -vI https://<hostname>/ 2>&1 | grep -i "issuer\|subject"   # expect "Let's Encrypt"
echo | openssl s_client -connect <hostname>:443 -servername <hostname> 2>/dev/null | openssl x509 -noout -dates
```

## 5c. DDNS for the WireGuard server tunnel's public endpoint

Only relevant once a WireGuard server-role tunnel (§10, e.g. `Bpl-Home`)
needs to accept peers connecting from *outside* the LAN, and this device's
public IP isn't static. Deliberately a **separate hostname** from
`CERT_CN`/`vpn.bpl.keekar.au` above — that one intentionally resolves to
this Pi's private LAN IP (§5b), kept off the public internet as a
deliberate hardening choice for the admin UI. This section's hostname
(`wg.bpl.keekar.au` in this deployment) is the opposite: it's meant to be
publicly resolvable to whatever this device's real WAN IP currently is.

`deploy/maintenance.sh`'s `cmd_ddns_update` (cron, every 10 minutes, see
`setup_cron` below) keeps that record current automatically using the same
Cloudflare API token already provisioned for §5b
(`/root/.cf-dns-token`) — no separate credential needed. It reuses the
existing "Edit zone DNS" scope rather than requesting a broader token,
per this project's least-privilege convention.

**One-time manual step, not automated by this script or `deploy.sh`**:
the DNS record must already exist before `ddns-update` will touch it — by
design, it only ever `PATCH`es an existing record, never creates one (a
safety choice: a typo'd hostname in `DDNS_RECORD_NAME` should fail loudly
rather than silently create an unexpected record in the zone). Create it
once, from the Pi (reuses the same token file, avoids copying the token
anywhere else):
```bash
sudo bash -c '
set -a; . /root/.cf-dns-token; set +a
ZONE_ID=<this zone'"'"'s ID — GET https://api.cloudflare.com/client/v4/zones?name=<your zone> with the same token>
CURRENT_IP=$(curl -s https://ifconfig.me)
curl -s -X POST "https://api.cloudflare.com/client/v4/zones/${ZONE_ID}/dns_records" \
  -H "Authorization: Bearer $CF_Token" -H "Content-Type: application/json" \
  --data "{\"type\":\"A\",\"name\":\"<your DDNS_RECORD_NAME>\",\"content\":\"${CURRENT_IP}\",\"ttl\":300,\"proxied\":false}"
'
```
`"proxied":false` (DNS-only/grey-cloud) is required, not optional —
Cloudflare's proxy only fronts HTTP(S)-shaped traffic; WireGuard is raw
UDP and would simply never arrive if proxied.

Update `CF_ZONE_ID`/`DDNS_RECORD_NAME` at the top of `deploy/maintenance.sh`
to match your own zone/hostname before deploying to a new zone/domain.

**Verify:**
```bash
sudo /opt/pi-config-ui/maintenance.sh ddns-update   # manual run; no output = already correct
tail -f /var/log/pi-config-ui-maintenance.log        # watch for the next scheduled run
```
If the record doesn't exist yet, this logs `ERROR: ddns-update: no DNS
record found for <name>` every 10 minutes (harmless, but noisy) until the
one-time creation step above is done.

Still required regardless of DNS being correct: a router-level port
forward (this tunnel's `ListenPort`/udp → this Pi's LAN IP) at whatever
physical location the device is currently at — see §10's note on this.
Moving the device to a new network means redoing the port-forward there
too; DDNS only solves the "which IP" half of the problem, not the "is
anything routed to me" half.

## 5d. Boot-health failsafe and update-rollback alert

The weekly `os-update` (Wednesdays 05:00) and `reboot` (Wednesdays 05:30,
deliberately right after `os-update` rather than days later, so a
regression is caught and confirmed/reverted the same morning) cron jobs
run completely unattended. `pi-config-ui-boot-check.service` (a root-run
oneshot unit, `deploy/pi-config-ui-boot-check.service`, `After=
pi-config-ui.service`) runs once per boot to catch the realistic failure
mode: the system boots, but `pi-config-ui` or a package it needs is
broken.

**What this does NOT cover, read first**: this Pi Zero W has no A/B
partition or "tryboot" bootloader scheme (that's Pi 4/5-only — confirmed
here via `vcgencmd bootloader_version` returning `unknown`, i.e. the
classic non-redundant boot flow). If a kernel/bootloader update makes the
device fail to boot at all, nothing running *on* that unbootable system
can fix itself — that needs physical recovery, same as before this
feature existed. Separately, and already true with zero code involved:
this Pi's hardware watchdog (Broadcom BCM2835) is active by default —
confirm with `dmesg | grep -i watchdog` (systemd pets it with a 1-minute
timeout) — so a full kernel panic or PID 1 hang already triggers an
automatic hard reboot on its own.

**What it does cover**: `cmd_os_update` (`deploy/maintenance.sh`), before
running `apt-get upgrade`, snapshots every package about to change into
`/etc/pi-config-ui/monitor/pkg-backups/<timestamp>/` — recording
`pkg=current_version` and best-effort copying that exact `.deb` from
`/var/cache/apt/archives/` *if it's still cached there*. This is not
guaranteed: Debian/Raspbian mirrors don't keep old versions downloadable
once superseded, so a package whose `.deb` had already been evicted from
the cache simply has nothing to revert to. On the next boot,
`cmd_boot_check`:
1. Polls `pi-config-ui`'s health the same way `cmd_health` does, up to
   ~3 minutes.
2. Healthy → if a snapshot was pending confirmation, clears it (this
   update was good) and exits quietly — the normal case, every boot.
3. Unhealthy → tries `systemctl restart pi-config-ui` once, rechecks.
4. Still unhealthy → if a snapshot is pending and a rollback hasn't
   already been attempted this cycle, reinstalls each package's preserved
   `.deb` (`apt-get install -y --allow-downgrades <path>`) and reboots
   once to apply. If a rollback was already attempted, or there's no
   pending update to blame, it does **not** reboot again — this is the
   loop-prevention guard.
5. Either way, once unhealthy, it writes an alert **unconditionally** to
   two places: the journal (`journalctl`, same as every other maintenance
   log line) and a plain file,
   `/etc/pi-config-ui/monitor/rollback_alert.json` — readable over SSH
   regardless of whether `pi-config-ui` itself can even start. When the
   app *is* up, the same data also renders as a pulsing red banner at the
   top of the dashboard (`GET /api/monitor/stats`'s `rollback_alert`
   field), with a Dismiss button (`POST
   /api/monitor/rollback-alert/dismiss`).

**Manually testing this**:
```bash
sudo /opt/pi-config-ui/maintenance.sh os-update   # creates a snapshot dir
ls /etc/pi-config-ui/monitor/pkg-backups/
sudo systemctl stop pi-config-ui   # simulate "won't come up"
# Note: `systemctl mask` does NOT work here to simulate this — it refuses
# to overwrite the real unit *file* deploy.sh installs at
# /etc/systemd/system/pi-config-ui.service ("File ... already exists"),
# since mask only auto-replaces an existing *symlink*. `stop` is enough:
# cmd_boot_check's restart attempt will just bring it back up, which is
# also exactly how the "recovered after restart" path gets exercised.
sudo /opt/pi-config-ui/maintenance.sh boot-check
cat /etc/pi-config-ui/monitor/rollback_alert.json   # only present if restart didn't recover it
```
The restart-recovery poll deliberately isn't a single fixed sleep: uvicorn
takes ~20s to start on this CPU (§14), and an earlier version of this
script that checked health only 15s after the restart falsely reported
"still unhealthy" — and wrote a false alert — for a restart that had
actually already succeeded. It now polls every 10s for up to 90s instead.

## 5e. Dashboard "Last downtime" stat

Separate from §5d's failsafe (though it shares the same state file): the
dashboard's System monitor page shows a "Last downtime" tile next to
Disk %, computed by `app/monitor.py` and rendered by
`app/static/dashboard.js`. Full rationale in
[`docs/PROJECT_NOTES.md`](PROJECT_NOTES.md), summarized here:

- This Pi Zero W has no hardware RTC and no `fake-hwclock` — the system
  clock is wrong from boot until `systemd-timesyncd` corrects it.
  `psutil.boot_time()` is **not stable before that correction** either (the
  kernel recomputes it whenever the wall clock steps), so a background
  heartbeat (`heartbeat_loop()`, every 60s, started from `app/main.py`'s
  `lifespan`) only ever reads/persists/compares it after confirming
  `/run/systemd/timesync/synchronized` exists.
- State lives in `/etc/pi-config-ui/monitor/state.json` (`last_seen`,
  `last_boot_time`, `last_downtime_seconds`) — the same file §5d's
  `cmd_boot_check` reads/writes its own keys into; each side only ever
  touches its own keys.
- Downtime is computed as `now - last_seen`, **not** `boot_time -
  last_seen` — `boot_time()` marks when the kernel started, which on this
  hardware is ~2 minutes before the device is actually usable (§0/§14);
  using it understated real downtime by the entire boot window in initial
  testing. `now`, read at the first heartbeat tick after the app itself
  has started, is a much closer proxy for "back on the network."
- A mere `Restart=on-failure` service bounce is not counted as downtime —
  only a `boot_time()` change (a genuine reboot) triggers a recompute;
  otherwise the previously-computed figure is restored from `state.json`
  (module-level state doesn't survive a process restart).
- `GET /api/monitor/stats`'s `last_downtime_seconds` (`null` until the
  first successful post-sync boot comparison, e.g. on a brand-new
  install) is rendered client-side via `formatDuration()` in
  `dashboard.js` as the largest two units (e.g. "2h 14m").

## 5f. Dashboard Uptime stat and Reboot/Shutdown buttons

**Uptime** (`app/monitor.py`'s `_uptime_seconds()`): reads the first field
of `/proc/uptime` (kernel-monotonic seconds since boot), deliberately
*not* `psutil.boot_time()` — that's the same wall-clock value §5e already
found unreliable pre-NTP-sync on this hardware. `/proc/uptime` is immune
to that whole class of bug, so no NTP-gating is needed here; it's a
simpler, independent stat from "Last downtime," just displayed in the
tile next to it via the same `formatDuration()`.

**Reboot/Shutdown** (`app/system.py`, new `/api/system/reboot` and
`/api/system/shutdown` endpoints): `pi-config-ui.service` runs
deliberately unprivileged (§7), so triggering a real reboot/shutdown
needs an explicit, narrow privilege grant rather than a blanket one.
`systemctl reboot`/`systemctl poweroff`, invoked by a non-root caller,
redirect to logind's D-Bus API specifically so polkit can gate them
per-user — the same mechanism (and same `subject.user === "pi-config-ui"`
pattern) `50-pi-config-ui-networkmanager.rules` already uses for
NetworkManager, just different action IDs.

**A real gotcha found via live testing, not just `pkcheck` in isolation**:
`pkcheck --action-id org.freedesktop.login1.reboot --process <pid>`
returning "allowed" is **not sufficient** to prove the button actually
works. The first version of `51-pi-config-ui-power.rules` granted only
the plain `org.freedesktop.login1.reboot`/`.power-off` actions, and
`pkcheck` against that action confirmed authorization — but a real
`systemctl reboot` invocation still failed with "Interactive
authentication required." `busctl monitor --system` while retrying
showed why: logind's `CheckAuthorization` call was actually for
`org.freedesktop.login1.reboot-multiple-sessions`, a *different* action
it switches to whenever any other logind session is active at the
moment — e.g. an admin SSH'd into the Pi at the same time they click
Reboot in the dashboard, a very plausible real scenario, not an edge
case. `51-pi-config-ui-power.rules` grants **all four**:
`reboot`/`reboot-multiple-sessions`/`power-off`/`power-off-multiple-sessions`.
No new root helper daemon needed either way, unlike WireGuard's
`pi-wg-helperd`. Independent of `maintenance.sh`'s existing scheduled
`reboot` subcommand (root, cron-triggered, §5) — this is a second,
separate path to the same underlying action for on-demand use from the
UI.

The dashboard's Shutdown button is deliberately styled and worded as more
severe than Reboot (`confirm()` text spells out that it will **not** come
back on its own, unlike the WireGuard "force" confirmation pattern this
reuses) — this hardware has no remote-wake path, so shutting it down
means someone needs physical access to power it back on.

**Verify — do the real thing, `pkcheck` alone isn't proof:**
```bash
PID=$(systemctl show pi-config-ui -p MainPID --value)
sudo pkcheck --action-id org.freedesktop.login1.reboot --process "$PID"                  # sanity check only
sudo pkcheck --action-id org.freedesktop.login1.reboot-multiple-sessions --process "$PID" # the one that actually matters if you're SSH'd in
sudo -u pi-config-ui systemctl reboot   # the real thing — confirmed working live, including while SSH'd in
```
Then `pytest` (mocks `_run_systemctl`, doesn't invoke the real binary).
Confirmed live end-to-end this way: the reboot actually happened, the Pi
came back up (~2.5 minutes, consistent with §0/§14), and `pi-config-ui`
was healthy again afterward with no rollback alert (expected — this
wasn't an update-triggered reboot, §5d doesn't apply here).

## 6. Groups before services — order matters

`pi-config-ui.service` references `SupplementaryGroups=pi-wg-helper`. If
that group doesn't exist when the unit is loaded, **systemd refuses to
start the service at all**. Create it before installing/starting anything:
```bash
sudo groupadd --system pi-wg-helper
```

## 7. Install both systemd services together

```bash
sudo apt-get install -y wireguard wireguard-tools iptables

sudo mkdir -p /opt/pi-wg-helperd
sudo cp deploy/pi-wg-helperd/helper.py /opt/pi-wg-helperd/
sudo chown root:root /opt/pi-wg-helperd/helper.py
sudo chmod 755 /opt/pi-wg-helperd/helper.py

sudo cp deploy/pi-wg-helperd.service /etc/systemd/system/
sudo cp deploy/pi-config-ui.service /etc/systemd/system/
sudo cp deploy/pi-config-ui-boot-check.service /etc/systemd/system/
sudo cp deploy/polkit-rules/50-pi-config-ui-networkmanager.rules /etc/polkit-1/rules.d/

sudo mkdir -p /etc/pi-config-ui/wireguard
sudo chown pi-config-ui:pi-config-ui /etc/pi-config-ui/wireguard
sudo mkdir -p /etc/pi-config-ui/monitor/pkg-backups
sudo chown pi-config-ui:pi-config-ui /etc/pi-config-ui/monitor
sudo chown root:root /etc/pi-config-ui/monitor/pkg-backups

sudo systemctl daemon-reload
sudo systemctl enable --now pi-wg-helperd
sudo systemctl enable --now pi-config-ui
sudo systemctl enable pi-config-ui-boot-check   # not --now: runs once per
                                                 # boot via multi-user.target,
                                                 # see §5d
```

**`iptables` must be installed explicitly** — Raspbian/Debian Trixie ships
nftables natively with no `iptables` compatibility shim by default. Any
WireGuard `PostUp`/`PostDown` line calling `iptables` fails with `command
not found` and `wg-quick` rolls back the entire interface it just brought
up if this isn't installed first. `apt-get install iptables` is a CLI
compat tool, not an extra running service.

**Why a separate helper daemon**: `pi-config-ui.service` deliberately
stays unprivileged (no root, `NoNewPrivileges=true`). Writing
`/etc/wireguard/*.conf`, running `wg-quick`, and `systemctl
enable/disable` genuinely need root — brokered over a Unix socket
(`/run/pi-wg-helperd/helper.sock`) by `pi-wg-helperd`, which runs as root
and validates every request's peer credentials. This is the
WireGuard-specific equivalent of the polkit brokering used for
NetworkManager below.

**Known trap — verify it hasn't regressed if hand-editing the unit**: the
helper's `RuntimeDirectory=` creates `/run/pi-wg-helperd` owned
`root:root`. If `RuntimeDirectoryMode` is `0750`, `pi-config-ui` (which is
in the `pi-wg-helper` *group*, not `root`) can't even traverse into that
directory to reach the socket, regardless of the socket file's own
permissions — every WireGuard-tab API call fails with a silent `EACCES`
*before ever reaching the daemon*, so nothing shows up in the daemon's own
logs either (that's the tell). The fix, already in
`deploy/pi-wg-helperd.service`, is `RuntimeDirectoryMode=0755`: the
directory becomes traversable, while the socket file itself (`0660
root:pi-wg-helper`, set inside `helper.py`) is what actually gates
read/write access. Confirm:
```bash
MAIN_PID=$(systemctl show pi-config-ui -p MainPID --value)
sudo cat /proc/$MAIN_PID/status | grep -i groups   # must include pi-wg-helper's gid
sudo ls -la /run/pi-wg-helperd/                     # dir drwxr-xr-x, socket srw-rw----
```

**The polkit rule** grants `pi-config-ui` exactly the NetworkManager
actions `app/network.py` needs (`settings.modify.system`,
`network-control`, `enable-disable-wifi`) — not a blanket allow. Verify
the exact action IDs against `pkaction` on your NetworkManager version if
Wi-Fi/interface actions fail with a permission error.

**Verify before moving on:**
```bash
sudo systemctl is-active pi-wg-helperd pi-config-ui   # both "active"
curl -sk -o /dev/null -w "%{http_code}\n" https://127.0.0.1:<port>/   # 303 (redirect to login) is healthy
sudo journalctl -u pi-config-ui --no-pager -n 20      # no repeated tracebacks
```

## 8. Port choice: 443 vs. a high port

`pi-config-ui.service` can bind port 443 directly
(`AmbientCapabilities=CAP_NET_ADMIN CAP_NET_BIND_SERVICE` on the
`ExecStart` line, no reverse proxy — the deployed config does this) or a
high port like 8443 (no extra capability needed). Whichever you choose,
`SSO_REDIRECT_URI` (§4) must match it exactly, including the presence or
absence of a port number — the Authentik client's registered redirect URI
must match byte-for-byte.

## 9. WireGuard client tunnel — only if this Pi dials *out* to a remote server

This is the "road-warrior" pattern (e.g. a Pi shipped to a remote site
that needs to reach a home/office network through an existing WireGuard
server elsewhere). **Not** the same as the WireGuard tab's server feature
(§10) — see `docs/PROJECT_NOTES.md` for running both simultaneously.

1. Generate a **unique** keypair for this device — never reuse a keypair
   from another device's exported config (two devices sharing one
   identity makes the server flip-flop between them; this happened once).
   ```bash
   wg genkey | tee privkey | wg pubkey
   ```
2. Get the resulting public key registered as a peer on the remote server
   **before** trying to connect — a tunnel with no matching peer looks
   "active" locally (interface up, keepalives sent) while showing `0 B
   received` forever, easy to mistake for a client-side bug.
3. Write `/etc/wireguard/<name>.conf` (`600`, dir `700`):
   ```ini
   [Interface]
   PrivateKey = <private key>
   Address = <assigned tunnel address>/32

   [Peer]
   PublicKey = <remote server's public key>
   AllowedIPs = <only the REMOTE subnets you actually need — see step 4>
   Endpoint = <remote server hostname/IP>:<port>
   PersistentKeepalive = 25
   ```
4. **Before enabling it, check `AllowedIPs` against `ip route` on this
   device — the single most damaging mistake made on this project.** If
   `AllowedIPs` includes a subnet the device is *already directly
   connected to* (its own current LAN), bringing the tunnel up adds a
   competing, higher-priority route for that subnet through the tunnel —
   breaking the device's own local network access, **including the SSH
   session used to configure it**. This has happened twice on this
   project: once a full SSH lockout requiring physical recovery, once a
   silent gateway-connectivity break (`ping <gateway>` failing) while the
   device otherwise looked fine.
   - **Prevention**: if the device is still on the subnet in question,
     either temporarily narrow `AllowedIPs` to exclude it for testing, or
     don't `enable`/`start` the tunnel until the device has actually been
     relocated, or confirm a real out-of-band recovery path (physical
     console, verified remote-management tool) exists first. Prefer
     `sudo wg-quick strip <name>` (renders the resolved config without
     applying it) over a live `enable --now` when SSH is the only access
     path.
   - **If it's already happened**: `sudo wg set <name> peer <pubkey>
     allowed-ips <corrected list>` updates the crypto/peer state live but
     **does not** remove the stale kernel route `wg-quick` already added
     — also run `sudo ip route del <subnet> dev <name>`, then rewrite the
     `.conf` file so the fix survives a restart.
5. Enable it only once step 4 is genuinely satisfied:
   ```bash
   sudo systemctl enable --now wg-quick@<name>
   ```
6. Day-to-day toggling from the WireGuard tab's Client connections
   section: use **Disconnect**, not Deactivate — Disconnect stops the
   tunnel without touching its boot-enablement, so a reboot still
   auto-reconnects. Deactivate (`disable --now`) is for actually
   decommissioning the tunnel.

## 10. WireGuard server tunnel — only if this Pi accepts *inbound* peers

Once §6-§7 are done, the WireGuard tab's "Create tunnel" form and
peer-management UI handle this end to end — no manual `.conf` editing
needed for a straightforward setup, and the tab enforces the same
`AllowedIPs`-overlap safety check as §9.4 automatically (with a `force`
override if you're certain).

Worked example from this deployment: the server tunnel is named
`Bpl-Home`, subnet `10.10.10.0/24`, `Endpoint = vpn.bpl.keekar.au:51820` —
distinct from the client tunnel `Syd-Home` (§9), which dials a different
location's server, so the two are unambiguous in both the admin UI and in
whatever hostname a connecting peer sees.

For the NAT/forwarding setup a server tunnel needs to actually give peers
LAN/internet access (the app's own tunnel-creation flow does not do this
automatically — it only writes the bare `[Interface]` block), append to
the tunnel's `[Interface]` section (safe to do — the helper's peer
add/remove logic treats everything before the first `[Peer]` block as an
opaque header and never rewrites it):
```ini
PostUp = sysctl -w net.ipv4.ip_forward=1; iptables -P FORWARD DROP; iptables -t nat -A POSTROUTING -s <tunnel-subnet> -o wlan0 -j MASQUERADE; iptables -A FORWARD -i <tunnel-iface> -o wlan0 -j ACCEPT; iptables -A FORWARD -i wlan0 -o <tunnel-iface> -m state --state RELATED,ESTABLISHED -j ACCEPT
PostDown = iptables -t nat -D POSTROUTING -s <tunnel-subnet> -o wlan0 -j MASQUERADE; iptables -D FORWARD -i <tunnel-iface> -o wlan0 -j ACCEPT; iptables -D FORWARD -i wlan0 -o <tunnel-iface> -m state --state RELATED,ESTABLISHED -j ACCEPT
```
Persist forwarding independently too, so it's visible/audited rather than
only implicit in the script: `/etc/sysctl.d/99-<name>-forward.conf`
containing `net.ipv4.ip_forward=1`.

**`iptables -P FORWARD DROP` is the actual enforcement of tunnel
isolation** — a default-`ACCEPT` `FORWARD` policy would silently let any
two interfaces bridge the moment both existed, regardless of whether any
rule explicitly allows it. Don't rely on "no rule references it" alone;
set the default-deny explicitly. No rule anywhere should reference a
different tunnel's interface name if they're meant to stay isolated.

Pick a tunnel subnet that doesn't overlap this LAN or any client tunnel's
remote subnets. Requires a router-level port-forward (this tunnel's
`ListenPort`/udp → this Pi's LAN IP) for peers connecting from outside the
LAN — outside the Pi's own control, a manual step on the home router.

### 10a. Renaming an existing server tunnel

`wg-quick` derives the interface and systemd unit name from the `.conf`
filename — there's no in-place rename, just a controlled cutover. This is
safe to do on a live tunnel with existing peers: peers authenticate by
public key and `Endpoint` host:port, never by interface name, so no
already-issued peer `.conf` needs to change or be redistributed.

1. `sudo wg-quick strip <old-name>` — inspect the resolved config,
   including the literal `PostUp`/`PostDown` iptables lines. **These
   reference the interface name literally** (`-i <old-name>`, `-o
   <old-name>` in the `FORWARD` rules above) and must be updated to the new
   name — the `MASQUERADE` line doesn't reference the iface name so needs
   no edit.
2. `sudo cp /etc/wireguard/<old-name>.conf /etc/wireguard/<new-name>.conf`,
   then edit the copy: replace `-i <old-name>`/`-o <old-name>` with `-i
   <new-name>`/`-o <new-name>` in `PostUp`/`PostDown`; leave the
   `[Interface]`/`[Peer]` blocks untouched.
3. `sudo systemctl disable --now wg-quick@<old-name>`
4. `sudo systemctl enable --now wg-quick@<new-name>`
5. Verify: `sudo wg show <new-name>` (interface up, existing peers still
   listed with prior handshake state preserved — confirms no peer
   re-registration is needed), `sudo iptables -L FORWARD -n | grep
   <new-name>` (rules present), `ip route` (no stale routes under the old
   name).
6. `sudo rm /etc/wireguard/<old-name>.conf` once step 5 confirms the new
   interface is healthy. Also check for `/etc/sysctl.d/99-<old-name>-forward.conf`
   (§10's forwarding-persistence step) — rename it too
   (`sudo mv /etc/sysctl.d/99-<old-name>-forward.conf
   /etc/sysctl.d/99-<new-name>-forward.conf`). Its *content* stays correct
   either way (`net.ipv4.ip_forward=1` isn't interface-specific), but a
   stale filename referencing a tunnel that no longer exists is exactly the
   kind of leftover that confuses the next person debugging this — this
   was missed once during the `wg1` → `Bpl-Home` rename on this project's
   real device and only caught later.
7. If this tunnel is listed in `deploy/maintenance.sh`'s `SERVER_TUNNELS`
   array, update the array in the repo and re-deploy so the live Pi's copy
   picks up the change: `./deploy/deploy.sh --only setup_cron` (or a full
   `deploy.sh` run) — otherwise the cron health-check keeps watching for a
   unit that no longer exists.
8. **If this tunnel has an entry in `/etc/pi-config-ui/wireguard/peers.json`**
   (i.e. it was originally created through the app's own "Create tunnel"
   form, not by hand over SSH), that entry is keyed by the *old* name and
   does not follow the rename — `app/wireguard.py`'s `create_peer` and
   `list_peers` both hard-404 with "Unknown tunnel" if
   `metadata["tunnels"].get(name)` is `None` (unlike `list_tunnels`/
   `set_tunnel_state`, which tolerate a missing entry — see the comments
   at `app/wireguard.py:113-117` and `:188-191`). The tunnel itself stays
   active and fine; only the "Add peer" form and Peers table for it break,
   silently, until you rename the key in `peers.json` to match (or, if the
   tunnel was created by hand and never had an entry at all, see the
   metadata-reconciliation note for that case instead). This exact gap was
   found on this project's real device during the `wg1` → `Bpl-Home`
   rename — see `docs/PROJECT_NOTES.md` Part 2.
9. If a router port-forward rule was labeled with the old name, relabel it
   for consistency — outside this repo's scope, a manual step on the home
   router.

## 11. Frontend: no build step, and a hard CSP rule

- `app/static/vendor/htmx.min.js` / `chart.umd.min.js` are vendored
  locally, not CDN-loaded — a tool whose job is fixing broken network
  config shouldn't itself need working internet access to render its UI.
- **Every page's JavaScript must live in an external `app/static/*.js`
  file, never inline in the template.** `app/main.py`'s CSP header is
  `default-src 'self'` with no `'unsafe-inline'` — `'self'` does not cover
  inline `<script>` blocks. An inline script is blocked **silently** by an
  enforcing browser: no console error, no failed request, the code just
  never runs. This shipped unnoticed once (every page's interactivity was
  dead, with no symptom beyond "the data never appears"). `tests/test_auth.py`
  regression-tests this (§13).
- **Checkbox-style `<label>`s need an explicit `.checkbox-label` class.**
  The generic `label { flex-direction: column }` rule (for the normal
  "text above input" pattern every text field uses) stacks a bare
  checkbox above its own trailing description text instead of placing it
  inline beside it. `app/static/style.css`'s `.checkbox-label` rule fixes
  this; apply it to any new checkbox `<label>`. Toggling a checkbox
  wrapper's visibility must use the `.hidden` utility class via
  `classList`, never an inline `style="display:..."` — inline styles beat
  the stylesheet rule and silently reintroduce the same inconsistency.
  Full incident writeup in `docs/PROJECT_NOTES.md` Part 1.

## 13. Tests

```bash
pip install -r requirements.txt -r requirements-dev.txt   # dev/CI only, never on the Pi
pytest
```

`tests/test_auth.py` covers two bugs that previously shipped silently:
1. **Session cookie `SameSite` must be `Lax`, not `Strict`** — `Strict`
   silently drops the cookie on the top-level cross-site redirect the IdP
   sends back to `/auth/callback`, so authlib can never find its stored
   `state`/PKCE `code_verifier`, and login fails 100% of the time with
   `MismatchingStateError`. The test asserts directly on the `Set-Cookie`
   header's `SameSite` attribute — a simulated login→callback round-trip
   via `TestClient` would **not** catch this, because `httpx`'s cookie jar
   doesn't enforce `SameSite` the way a real browser does.
2. **No page may ship a `<script>` tag without `src` that has real
   content** — the CSP-blocks-inline-script bug from §11. Auth is bypassed
   via FastAPI's `dependency_overrides` on `current_user`, not a real
   login.

`tests/conftest.py` sets dummy `SSO_*`/`SESSION_SECRET` env vars before any
`app.*` import (`app.config.Settings()` is instantiated at import time and
fails fast without them). `pytest.ini` sets `pythonpath = .` so `app` is
importable without installing the project as a package.

## 15. Miscellaneous operational notes

- `sudo` on these Pis is password-protected by default, not passwordless.
  A `sudo -n true` success can be a leftover cached ticket (expires ~15
  min after last use) — don't assume scripted/unattended `sudo` keeps
  working across a long session unless you've explicitly installed a
  `NOPASSWD` `sudoers.d` drop-in (validate with `visudo -c` before
  installing — a broken sudoers file can lock out sudo entirely).
- This device class has been observed to reboot on its own mid-deployment
  at least once, cause unidentified (worth watching for under-voltage/
  stability issues on Pi Zero W hardware). `/tmp` is tmpfs and does not
  survive a reboot — don't stage multi-step installs there without
  re-checking after any gap.
- `cloud-init`, if present, has been flagged as a possible cause of slow
  boot on this device class — check `test -e /etc/cloud/cloud-init.disabled`
  before assuming it's off.

## 16. Separating a client-tunnel peer identity from another device sharing the same remote server

Applies to any client-role tunnel (e.g. `Syd-Home`) that dials into a
remote WireGuard server another device (e.g. a laptop) also connects to.
Two devices must never present the same public key/address to that
server — see `docs/PROJECT_NOTES.md` Part 3 Incident 1 for what happens
when they do (the server flip-flops between them; only one holds a
session at a time).

**Step 1 — check the current state:**
```bash
sudo cat /etc/wireguard/<name>.conf        # note Address= and PrivateKey=
wg pubkey < <(sudo wg show <name> private-key)   # derive this device's current public key
```
Compare against the other device's known public key (read from its own
WireGuard app). If they match, this device is still sharing that identity —
continue to step 2a. If they already differ, skip to step 3 (only the
remote server's peer registration may still need creating/confirming).

On the remote server's admin UI (for a pfSense WireGuard server: **VPN →
WireGuard → Peers**), confirm whether a peer already exists for this
device's public key, and that the address you intend to assign isn't
already in use by another peer's Allowed IPs.

**Step 2 — give this device its own identity (only if step 1 found a
shared key):**
```bash
wg genkey | tee privkey | wg pubkey   # new, unique keypair — never reuse another device's
```
Edit `/etc/wireguard/<name>.conf`, replacing only `PrivateKey` and
`Address` with the new key and a freshly-chosen, unused tunnel address;
leave the `[Peer]` section (remote server's public key, `AllowedIPs`,
`Endpoint`) untouched. Restart: `sudo systemctl restart wg-quick@<name>`.

**Step 3 — register the new identity as a distinct peer on the remote
server.** For a pfSense WireGuard server (this project's `Syd-Home` target
is pfSense 2.8.1-RELEASE, WireGuard package 0.2.9_6): **VPN → WireGuard →
Tunnels**, open the relevant tunnel, its **Peers** tab → **Add Peer** —
give it a Description that visibly distinguishes it from the other
device's peer (and rename that other peer's Description too, if it's not
already explicit), set **Public Key** to this device's key from step 1/2,
**Allowed IPs** to the fresh address chosen above, then **Save → Apply
Changes**.

**If pfSense's "Add Peer" form set (or auto-generated) a Preshared Key**,
copy its exact value into this device's `.conf`, as a `PresharedKey =`
line inside the `[Peer]` block (any line between `PublicKey` and
`AllowedIPs` works). A PSK set on only one side fails the handshake
**silently** — `wg show` on both ends will report nonzero `sent`/`received`
byte counts (handshake-initiation packets still count as traffic) while
the server's status page shows "Latest Handshake: never" indefinitely, and
there's no error anywhere pointing at the actual cause. If a rename/re-key
leaves a tunnel handshaking-but-never-completing after several
`PersistentKeepalive` intervals with an otherwise-correct public key and
address, check this first.

**Step 4 — verify:** `sudo wg show <name>` on this device shows a recent
handshake with non-zero `received` bytes (not just keepalives with no
reply); the server's own status page shows the new peer handshaking
independently of the other device's peer, and both can be connected at the
same time without either dropping.

## 17. Routing a single LAN device's traffic through a client tunnel (e.g. a camera → remote NAS)

Applies when some *other* device on this Pi's LAN (not the Pi itself)
needs its own traffic carried through a client-role tunnel (e.g.
`Syd-Home`) to reach a specific remote subnet — for example, an IP camera
whose static-IP menu lets you set its own Gateway/DNS, and you want it to
send its stream/traffic to a NAS reachable through that tunnel. This is
one-directional (the LAN device initiates; nothing dials back into it) —
see §17a below if the reverse direction is also needed.

**Prerequisite — same-subnet requirement, checked every time the network
changes:** the device's configured Gateway must be an address the Pi
actually holds on that same LAN segment, which means the device's static
IP/subnet must also match whatever subnet the Pi is currently on. This
Pi is designed to move between physically different networks (see
`docs/PROJECT_NOTES.md`'s DDNS section) — a different router at a new
location almost certainly means a different DHCP subnet, even with an
identical Wi-Fi SSID/password. Before relying on this setup at a new
location: check the Pi's current LAN address (`ip -4 addr show wlan0`),
then re-point the device's static IP/Gateway to match if it's changed.

**On the Pi**, add to the client tunnel's `PostUp`/`PostDown` (single
semicolon-separated line each, matching the style already used for
`Bpl-Home`'s NAT rules in §10) — scoped tightly to the specific device's
IP and the specific remote subnet(s) already in that tunnel's own
`AllowedIPs`, never a blanket LAN↔tunnel bridge (this project's client and
server tunnels are deliberately kept from bridging into each other, see
`docs/PROJECT_NOTES.md` Part 2):
```ini
PostUp = CAM_IP=<device LAN IP>; sysctl -w net.ipv4.ip_forward=1; iptables -A FORWARD -i <lan-iface> -o <tunnel-name> -s $CAM_IP -d <remote-subnet> -j ACCEPT; iptables -A FORWARD -i <tunnel-name> -o <lan-iface> -d $CAM_IP -m state --state RELATED,ESTABLISHED -j ACCEPT; iptables -t nat -A POSTROUTING -s $CAM_IP -o <tunnel-name> -j MASQUERADE
PostDown = CAM_IP=<device LAN IP>; iptables -D FORWARD -i <lan-iface> -o <tunnel-name> -s $CAM_IP -d <remote-subnet> -j ACCEPT; iptables -D FORWARD -i <tunnel-name> -o <lan-iface> -d $CAM_IP -m state --state RELATED,ESTABLISHED -j ACCEPT; iptables -t nat -D POSTROUTING -s $CAM_IP -o <tunnel-name> -j MASQUERADE
```
Add one `-d <remote-subnet>` FORWARD line per subnet in the tunnel's
`AllowedIPs` if there's more than one. No extra `ip route` is needed — the
tunnel's own `AllowedIPs` already installs the kernel route to the remote
subnet(s) when the tunnel comes up. Also persist forwarding independently
(§10's convention): `/etc/sysctl.d/99-<tunnel-name>-camera-forward.conf`
containing `net.ipv4.ip_forward=1`.

**`MASQUERADE`, not a bare route-through**: the remote side (e.g. pfSense)
only knows about this Pi's own tunnel address, not the LAN device's real
IP — without NAT, the remote end would have no route back for reply
traffic, and would need its own routing/peer-config changes to learn one.
`MASQUERADE` avoids touching anything on the remote end at all, at the
cost of the remote side seeing the tunnel's own address as the traffic's
source, not the LAN device's real IP — acceptable for a one-way
"send-to" relationship, worth reconsidering if the remote side needs to
distinguish/allowlist by the device's real IP.

**On the LAN device itself** (its own static-IP configuration screen, not
this Pi): IP address and subnet mask matching the Pi's current LAN subnet
(see prerequisite above); Gateway = this Pi's current LAN IP; DNS is only
relevant if the device needs to resolve a hostname rather than dial the
remote NAS by raw IP — a public resolver (e.g. `1.1.1.1`) is fine
otherwise.

**Verify** (once the device is powered on and actually sends traffic):
```bash
sudo iptables -L FORWARD -n -v | grep <device-ip>       # packet/byte counters should climb
sudo iptables -t nat -L POSTROUTING -n -v | grep <device-ip>
sudo conntrack -L -s <device-ip>                          # active flows, if conntrack is installed
ip route | grep 192.168.1.0/24                            # unaffected safety check — must still be wlan0
```

### 17a. Adding the reverse direction (remote side dialing back into the device)

If something on the remote side also needs to initiate a connection to
the LAN device (e.g. an NVR pulling an RTSP stream on demand, rather than
the device pushing out), add a DNAT rule forwarding a port on the tunnel's
own address to the device, and point the remote side at `<this Pi's
tunnel address>:<port>` rather than the device's real LAN IP — no changes
needed on the remote end for this either, for the same reason `MASQUERADE`
above avoids them:
```ini
PostUp = ...; iptables -t nat -A PREROUTING -i <tunnel-name> -p tcp --dport <port> -j DNAT --to-destination <device-ip>:<port>
PostDown = ...; iptables -t nat -D PREROUTING -i <tunnel-name> -p tcp --dport <port> -j DNAT --to-destination <device-ip>:<port>
```
Remote-side discovery protocols relying on LAN multicast (e.g. ONVIF
auto-discovery) won't work across a routed tunnel regardless — add the
device manually by the tunnel address on whatever's connecting to it.
